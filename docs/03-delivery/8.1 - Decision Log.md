## Phase 2 step 1: Tier 0 memory check (8 Nov 2026)

The SP2 figure of 710MB included torch and transformers, which the `gliner` Python package imports. The model worker will use onnxruntime only (as SP1 did), so I measured that (Windows, int8 models, 1 thread, one session each, Python 3.12 with numpy, a stand-in for the Rust worker):

| Piece | Working set | Private | Note |
|---|---|---|---|
| Runtime baseline (Python, numpy, onnxruntime) | 54 MB | 31 MB | Smaller in Rust; not measured |
| Router (MiniLM int8) after load | 88 MB | 61 MB | about +35 MB over baseline |
| Extractor (GLiNER-small int8) after load | 248 MB | 221 MB | about +195 MB over baseline |
| Extractor after 20 inferences | 253 MB | 222 MB | Peak while loading 382 MB |

Both models in one worker should come to about 280 to 300MB. Add Core (14MB) and idle is about 300MB: PR1 is met only on the edge, with the worker loaded, and clearly met when the worker has exited (D27: 14MB). The 710MB number was a packaging artefact, not the model; my earlier note that idle would be about 0.8GB was wrong.

**Decision (recommended, D32):** keep the two-model worker lean (onnxruntime plus tokenizers, no torch), load the router first, load the extractor only when the rules cannot fill a slot, and let the worker exit after idle. Report PR1 as "under 300MB, worker unloaded; about 300MB with Tier 0 loaded". The "Phase 2 done when" wording (under 300MB with Tier 0 loaded) will not be met strictly, so either the worker idle-exit counts or PR1 becomes 350MB. Needs your call.

Separate risk: SP2 failed on accuracy (62% on a blind set), so extraction quality in Phase 2 comes from rules plus runtime gazetteers (contacts, apps, files), not the model. Not yet re-measured on the 8GB laptop; the numbers above are from a busy dev PC.

## Phase 2 step 4: resolver and context (8 Nov 2026)

- **Resolver** (`core::resolver`): follows each slot's `resolve` order. `selected_file` is used for "this" or nothing said; `named_file` is a fuzzy match (exact word, contained word, one typo) over Downloads, Documents and Desktop; `recent_download` is used for "the latest download" or when nothing is said or selected; `usual_*` reads the setting `usual.<type>` when nothing is said. A file now carries `name` and `path`, so `{file.path}` works and the WhatsApp skill is no longer refused before the confirm.
- **Ties (FR4):** files within 0.08 of the best score make one question with up to three options; dismissing it cancels. A name that matches nothing says "I couldn't find X." and never confirms or sends.
- **Context service** (`core::context`): bounded walk (depth 3, 20,000 files, skips `node_modules`, `.git`, `AppData`, partial downloads), nothing stored. Explorer's selection is read when the hotkey is pressed (`adapter-windows::explorer`, read-only, no keys or clicks sent) and kept as a snapshot.
- **Verified live (8 Nov):** the Explorer read passed its `--ignored` live test (new Explorer window with a file selected, read back by window handle). Not yet tried through the real hotkey path in the app. The snapshot arrives a few hundred ms after the hotkey, so a request sent in that moment sees no selection.
- **Still stand-ins:** contacts and apps pass the user's words through (`named_contact`, `named_app`); real contact resolution and an installed-apps list for slots are later. Usual choices are only read; writing them after a successful task (FR10) is step 7. The file index is rebuilt per request (fast enough for now; cache if it shows up in timings).

## Closed lists and contacts (9 Nov 2026)

Closes the gap "the app does not pass its installed-apps and contacts lists to the router" and the "contact resolution" item.

- **Installed apps** (`AppIndex::names`, non-blocking) are asked for at every request through `Flow::with_app_names` and go to the router/extractor as `ContextNote.apps`, and to `named_app`. A name on the list becomes the real app name; two that fit make one question; a name on no list passes through as said (the index can be minutes old and the connector refreshes on a miss).
- **Contacts, options compared.** (A) Read an OS store: Windows People / `Windows.ApplicationModel.Contacts` needs a packaged app identity and a synced Microsoft account, and the People database is not a documented, readable file; Outlook COM only helps classic-Outlook users. Google needs OAuth registration. Rejected for V1. (B) A local `contacts` table in our own database, filled by use and by importing vCard (`.vcf`) files; works with no account, shows a number when a vCard had one, can be edited or forgotten later (Phase 5). (C) Derive the list from the `defaults` table (distinct values of slot type `contact`): no migration, but no numbers, no import and no way to forget one. **Chosen: B**, still using the learned-defaults mechanism for the words-to-person memory (a "which Ved" answer is remembered by phrase; a usual contact is read from `defaults`).
- **Remembering.** After a task succeeds, each contact the user named is saved (`Store::remember_contact`, table `contacts`, migration 2) and counted. A name typed in lowercase is saved capitalised. Not learned: a cancelled or failed task, the test send skill (`category: testing`), groups ("ved and rahul", "all my contacts"). `%USERPROFILE%Contacts*.vcf` is imported at start (repeatable).
- **Matching** (`core::known`): full name first; otherwise every word said must be a whole word of the name ("ved" fits "Ved Narvekar"); one fit is the person, several make the question (T94). No typo matching: a send goes to a real person. The confirm card shows `{contact.label}`, the name with the number when known. **Every send still needs its confirm**; nothing in the policy changed.
- **Tests.** Unit tests in `store`, `core::known`, `core::flow`, `adapter-windows::apps`. Test set: T94 and T52 added (both need the model), T01 now runs with an installed-apps list. With the real worker the runner passes 50 of 50 (the old 48 plus these two); without the worker, 30 of 30.
