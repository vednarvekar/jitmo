# 9. Skills Audit (9 Nov 2026)

An end-to-end QA pass over every shipped skill: relevance of what the bar says, completeness for bare and
partial commands, robustness to typos / slang / Hinglish / adversarial input, honesty of each connector, and
the bar's behaviour in each state. Evidence comes from a reusable harness (section 8) that drives the **real
`Flow`, the real router (model worker, NER extractor) and the real connectors** over 643 messy inputs, with
the PC replaced by a recording simulator, so every number below can be re-run.

* **Baseline** = commit `855a638` (the state the user reported bugs against).
* **After** = commit `36c051c` (the concurrent fixes: timer asks how long, skill `title:` for "Did you mean",
  Spotify Play-button matching, focus handling). Both were run with the same corpus; both columns are given.
* Nothing in product code was changed by this audit. Added files: see section 8.

> **How to read the pass rates.** Every corpus line states what a *good* assistant does (ask a follow-up for a
> missing slot, never show an example sentence, never claim what it did not verify). A failing line is a
> finding, not a regression. Pass rate is therefore a measure of distance from the ideal, not a product score.
> About 100 of the 643 lines are "partial" or "ambiguous" inputs where the ideal is a question.

## 2. Findings, ranked

Severity: **P0** wrong or unsafe action, a false claim, or a crash. **P1** a typical request fails or misleads.
**P2** friction, a gap a user will hit. **P3** polish. "Status" says whether the concurrent fixes changed it
(verified by re-running the corpus on `36c051c`).

### P0

**F01. Do Not Disturb "until X" is a promise nothing keeps.** `system.dnd`
* Input: "don't disturb me for an hour". Shown: "Do Not Disturb is on until 11:00 AM." (and Undo).
* Observed: DND is switched on and **stays on for ever**. `dnd.rs:13-14` says "The app scheduler must turn DND
  off at that time", `dnd.rs:317` puts `until` in the Output and comments "The app scheduler turns it off". No such
  scheduler exists: `app/src-tauri/src/scheduler.rs` and `core/src/scheduler.rs` only fire reminders. While DND is
  on Windows also suppresses this app's own reminder and timer toasts (see F07), so the failure compounds.
* Related: a duration the parser cannot take is dropped without a word. `dnd for 0 minutes` and
  `dnd for 5000 hours` both answer "Do Not Disturb is on." (`dnd.rs:157` returns `None` for `mins <= 0` or
  `> 24*60`, and the caller treats `None` as "no duration").
* Expected: either turn it off at the time (schedule in the same store the reminders use: a row of kind
  `dnd_off`), or do not say "until". Refuse or ask for a duration outside 1 minute to 24 hours.
* Status: open.

**F02. A panic in any connector kills the core thread; the bar then hangs on "Working..." for ever.** `reminders.timer`
* Input: `set a timer for 1000000000000000000000 minutes` (a typo with extra zeros is enough).
* Observed: `chrono` panics (`TimeDelta::seconds out of bounds`) in `reminders.rs:53`
  (`Duration::seconds((count * unit.num_seconds() as f64).round() as i64)`). `service.rs:106` calls
  `flow.handle` with no `catch_unwind`, so the "jitmo-core" thread dies. Every later request is sent into a channel
  nobody reads. The bar shows "Working..." for ever; Esc sends `Cancel` that nothing reads; `hideOnBlur` is false
  while working, so the always-on-top bar cannot even be dismissed by clicking away (`state.ts hideOnBlur`).
* Same parser, no panic but wrong: `timer for 99999 hours` answers "Timer set for 99999 hours."; `timer for -5
  minutes` answers "Timer set for 5 minutes." (the minus is dropped by the regex, `reminders.rs:39`).
* Expected: cap and validate (1 second to 24 hours for a timer, say so), wrap `flow.handle` in `catch_unwind`
  and answer "Something went wrong." so one bad request can never take the engine down.
* Status: open.

### P1

**F03. "Play <song>" can play a different song, and "Playing X" is claimed without checking the track.** `music.play`
* User bug 3 (`play janam janam song`). Root causes found, in order of impact:
  1. (fixed at `d36c456`) `PLAY_FIRST_RESULT_SCRIPT` pressed the top-left-most "Play" button, which on a Spotify
     search page is often the Top-result card of another thing (`spotify.rs` baseline lines 46-68).
  2. The search query is the user's sentence with the verb cut off, so typo'd verbs, filler, the assistant's name
     and Hinglish go into the search: `plya arijit singh` searches "plya arijit singh"; `yo play despacito pls`
     searches "yo play despacito pls"; `hey jitmo play kesariya` searches "hey jitmo play kesariya"; `spotify kholo`
     (routed to music.play) searches "spotify kholo" and answers "Playing spotify kholo on Spotify."; `gaana band
     karo` (meant: stop the music) **starts a search and plays**, answering "Playing gaana band karo on Spotify."
     `parse_search` (`spotify.rs:131`) only strips a fixed list of leading verbs and "on spotify".
  3. The claim "Playing {q} on Spotify." (`spotify.rs:310`) rests on the global `PlaybackStatus == Playing`, not on the
     track. If something else was already playing, or the pressed button started something else, it still says it.
     The media session exposes the title and artist; read them back and compare.
  4. Generic words ("song", "the", "by") stay in the query (`play kesariya song`).
* Expected: normalise the query (strip verb typos via the router's `media` span, not the raw sentence), press the
  matching button, read the title back, and say "Playing <title> by <artist>" or "Opened the search for X; press Play".
* Status: cause 1 fixed; 2, 3, 4 open.

**F04. "Did you mean" and the choice list showed another skill's example sentence, not the user's request.** all skills
* User bug 2. `flow.rs` baseline `:363` printed `Did you mean: {describe(skill)}?` and `describe()` (`:619`) returned
  `skill.examples.first()`. Observed in the corpus: `who wrote Pride and Prejudice` -> "Did you mean: what's the capital
  of Australia?"; `remind me tomorrow at 9am...` -> "...remind me to call mom at 6pm?"; `awaaz kam karo` -> "...play
  arijit singh on spotify?"; `open chrome` -> "Did you mean: open {app}?" (raw placeholders in 45 cases); `who is the
  best cricketer` -> choices "play arijit singh on spotify | what's the capital of Australia | will it rain tomorrow".
* Status: fixed at `d36c456` with `title:` per skill (G2 45 -> 0, G3 150 -> 0). Residual: see F20 (generic choices for
  chit-chat) and the example text still inside error hints (F06).

**F05. The verifier replaces an honest answer with "I couldn't confirm that it worked", after the action has run, and blocks the core thread for seconds.** `music.play`, `system.lock`
* `play despacito` with a Spotify that never reports Playing: `execute` returns the honest "Opened Spotify on a search for
  despacito. Press Play on the first result." Then `flow.rs:588` runs the check, which is `is_playing_soon()` again
  (4 reads x 0.8 s), twice (`verifier.rs` retries once): the user gets **"I couldn't confirm that it worked. Please check
  spotify."** (a failure) about 10 s later. The honest message is lost, Spotify is already open, and the single core thread
  is blocked meanwhile (G12: 3 cases over 3 s; `spotify.rs:236` sleeps, `spotify.rs:336`).
* `lock my laptop` where the lock screen is not detected: 6 s of polling (`system_controls.rs` lock check: 6 x 500 ms,
  twice) then "I couldn't confirm ... Please check system_controls." (leaks the connector name).
* Expected: a check must be able to *downgrade* a result to the connector's own honest message, not turn a done action
  into a failure; and checks must be fast (one read) or asynchronous.
* Status: open.

**F06. Bare and partial commands end in an error that is really a question, with nowhere to answer.** 18 of 24 skills
* G10 fired 23 times, and many more "I'm missing the ..." / "I couldn't find ..." cases. Examples (all verified):
  `volume` -> "I'm not sure what to change. Try "turn the volume down"."; `wifi` / `turn wifi` -> FAILED "Do you want it on or off?";
  `music` -> FAILED "Should I pause, resume or skip?"; `remind me` -> FAILED "When should I remind you? Try "remind me to call
  mom at 6pm"."; `search` -> "I'm missing the file."; `open` -> confirm "Did you mean: open {app}?" then "I'm missing the app.";
  `weather` -> FAILED "Which place? Say, for example, 'will it rain in Pune tomorrow'"; `sunrise` -> a **Done** answer
  "Which city? Try "sunset in Pune"..."; `go to` / `google` / `search youtube` -> "Which website? Try "open Amazon"." /
  "What should I search for? Try "search YouTube for pasta"."; `timer` -> "You have no timers set." (user bug 1: it *listed*
  instead of asking; `flow.rs:846 timer_command` treats any two-word-or-fewer sentence containing "timer" as a listing).
* Root cause: see S1/S2. A connector can only return `Ok` or `Err(text)`; the flow can ask only for a slot of a
  free-text kind (`FREE_TEXT_KINDS`, `flow.rs:728`), and 18 skills declare no slots at all (lint L2), so every missing
  value reaches the connector as a whole sentence and comes back as a failure string. A question in a failure string is shown
  for 8 s and then the bar closes; the user must retype everything.
* Expected: a quick-choice question where natural (timer: 5 / 10 / 15 / 30 / 60 / custom; volume: up / down / mute / a number;
  radio: on / off; DND: for an hour / until 6pm / off; remind: in 1 hour / this evening / tomorrow 9 am / custom) and a typed
  question otherwise, then run with the answer.
* Status: **timer fixed** (`start a timer`, `timer`, `new timer` now show the 5/10/15/30/60/Custom choice); everything else open.

**F07. A timer or reminder can be "set" and never be seen.** `reminders.timer`, `reminders.remind`
* Truthfulness: the connector only writes a row. The notification is a Windows toast from a loop that polls every 10 s
  (`app/src-tauri/src/scheduler.rs:27`), so a "45 second timer" fires between 45 and 55 s. If the toast fails (focus assist,
  notifications off, **DND on, which this app itself can switch on for ever (F01)**) the row is marked done anyway and the only
  trace is `eprintln!` (`core/src/scheduler.rs:90`). The user saw "Timer set for 10 minutes." and nothing ever rings.
* Every timer is stored with the text "Timer" (`reminders.rs`), so `timer 10 minutes` twice makes two indistinguishable rows
  (verified: pending = 2), the list says "Timer: 7 min left" twice, and a reminder whose text is exactly "Timer" is treated as a timer.
  The check `pending.iter().any(|r| r.text == p.what)` is satisfied by an older timer, so it cannot prove the new one was saved.
* Expected: fire on time (poll every 1 s, or schedule a thread wake-up), retry a failed toast, tell the user when
  notifications are off, number the timers or label them ("pasta timer").
* Status: open.

**F08. Reminder parsing silently picks the wrong day, and pollutes the text.** `reminders.remind`
* `remind me on 15 nov at 3pm to call mom` -> "Reminder set for 3:00 PM **today**: On 15 nov to call mom."
* `remind me yesterday at 5pm to call` -> "Reminder set for 5:00 PM today: Yesterday to call."
* `remind me at 6pm tmrw to call mom` -> "6:00 PM today: Tmrw to call mom." (and `tommorow`)
* `remind me at 6pm` -> "6:00 PM today: Reminder." (nothing to be reminded of); `remind me tomorrow` -> "9:00 AM tomorrow: Reminder."
* `remind me in 2 days ...`, `remind me next week ...` -> FAILED "When should I remind you?" (G10, with "call mom" leaked from the hint).
* Timers: `timer for ten minutes`, `fifteen min` -> "How long should the timer run?" even though the user said how long; `10 mintue timer`,
  `timr` -> failure; `ek ghante ka timer` unsupported.
* Root cause: `reminders.rs:79 parse` has no calendar-date, "tmrw", "yesterday", "next week", "N days" or number-word grammar,
  and the leftover words go into the reminder text. A date it cannot read should be refused, not defaulted to today.
* Expected: parse or ask; never state a day different from the one typed; never save the placeholder "Reminder".
* Status: open (timer length question fixed for the empty case only).

**F09. Common requests are routed to the wrong skill, or declined.** router + skills
* `2+2` -> "I can't do that yet."; `1,000 + 500` -> "I can't plan that right now. Try a simpler request." (CHAINED: "+"
  trips the chain flag); `0.1+0.2` -> confirm "Open an app?" then "I'm missing the app."
* `every Monday at 10 remind me to send the report` (**the skill's own example sentence**) -> "I can't do that yet." (the
  model's label has no skill, `router.rs map_worker_result_with`).
* `remind me tonight to lock up` -> confirm "Lock the PC?" (Enter locks the laptop).
* `set an alarm for 7am` / `alarm for tomorrow 6 am` -> timer skill -> "Reminder set for 7:00 AM tomorrow: **Set an alarm for.**"
* `send money to ved` and `send this file to ved on whatsapp` -> `stub.send` (F11).
* `pause the timer` -> "How long should the timer run?"; `pause the video` -> pauses Spotify; `mute spotify` -> pauses;
  `play and pause` -> Paused.
* `search` / `search for` -> files.find "I'm missing the file."
* Expected: arithmetic always reaches calc; an unsupported recurring form says so; destructive-sounding neighbours
  (`lock`, `send`) never win on a weak match.
* Status: open.

**F10. Opening apps: several resolver bugs.** `apps.open`
* `open app` **opens WhatsApp**: `known.rs:122 match_app` accepts any installed app whose squashed name *contains* the
  word (>=3 chars): "app" is inside "whatsapp". Same hazard for `open set`, `open pad`, `open ice`...
* `start the calculator` -> "the calculator isn't installed." (the span keeps "the"); `open up spotify please` -> "up spotify
  please isn't installed."; `open edge or chrome` -> "edge or chrome isn't installed."; `open vs code` and every typo
  (`spotfy`, `notpad`, `calcualtor`) -> "<word> isn't installed." with no suggestion although the app is installed
  (`resolver.rs:290` passes unmatched words through as said, there is no fuzzy match).
* `open notes` and `open photo.jpg` are routed to apps.open ("notes isn't installed.") although those files exist.
* `open` -> confirm "Open an app?" (after fix) then "I'm missing the app." No question.
* `open xyzzyabc` is honest ("xyzzyabc isn't installed."). `open ../../windows/system32/cmd.exe` and `open calc.exe & del *.*`
  only reach an installed-app lookup, so nothing unsafe runs (verified: no connector call carried a shell fragment).
* Expected: trim determiners and politeness, fuzzy-match against installed apps and **ask** ("Did you mean Spotify?"),
  whole-word match only, prefer files when the word has an extension or matches a file.
* Status: open (the confirm text is now readable).

**F11. A test skill is registered in production, and its pattern hijacks sends.** `stub.send`, `whatsapp.send_file`
* `registry.rs load_skills` ships `stub.send` ("send {text} to {contact}") but not `whatsapp.send_file`. Any "send X to Y"
  matches the stub with score 0.9, ahead of the model (`router.rs`, unlabeled-skill rule): `send money to ved` -> confirm
  `Send "money" to ved?` then "This was a test: nothing was really sent."; `send this file to ved on whatsapp` -> confirm
  `Send "this file" to ved on whatsapp?`, contact = "ved on whatsapp". The final message is honest, but the confirm card
  promises a real send, and the only honest decline ("WhatsApp is not available yet") never appears.
* Expected: do not register test skills in the app; when a real skill is missing, say so by name ("Sending files on
  WhatsApp is not built yet").
* Status: open.

**F12. Volume and brightness: the number and the word forms are not understood.** `system.volume`

  `turn it up`, `mutee`, `turn the volme down` -> FAILED "I'm not sure what to change. Try "turn the volume down"." (G10).

* Root cause: `parse_adjust` (`system_controls.rs:197`) needs " to " or the words set/at before a number, has no number words,

* Expected: a bare number after the noun is "set"; ask up / down / mute / a number for the bare noun; clamp and say so.

**F20. Declines and low-confidence questions are generic.** all

### P2

**F21. Keyboard focus is not kept in the input (user bug 4), only improved.** `app/src/App.tsx`
* After the fix: Tab re-focuses, clicking elsewhere no longer takes focus, and a blur returns it. Still: the input is
  `disabled={!typing}` (`App.tsx:346`) in the **confirm and choice** phases, and it is **unmounted** while working, done and failed
  (`showStatus`, `App.tsx:264`), so for five of the seven phases no element holds focus; keys work only because of the window-level
  listener. A disabled input cannot hold focus whatever `onBlur` does.
* Fix: `readOnly` instead of `disabled`, and keep the input mounted (visually hidden) in the status phases.
* Status: partly fixed.

**F22. Esc does not stop a running action, and a bar that lost the window focus cannot be closed.** `app/src/App.tsx`, `core/src/service.rs`
* Esc during "Working..." sends `Cancel`; `service.rs run` ignores a `Cancel` that arrives while `flow.handle` is running and the flow
  checks for it only at its next prompt, so a 10 s Spotify action or an 8 s app-launch check cannot be abandoned.
* `hideOnBlur` is false in working / confirm / choice / asking (`state.ts`), so if the user clicks into another window during a confirm,
  the bar stays on top with no focus; Esc no longer reaches it. There is no timeout (stated in `service.rs`).
* Status: open.

**F23. After a result, the first key typed is dropped in some cases.** `app/src/App.tsx:208`
* From code, not run: the "type to replace the result" branch requires `e.key.length === 1 && !e.ctrlKey`, so an emoji (a surrogate pair,
  `key.length === 2`), an IME composition, a dead key, and **Ctrl+V** do nothing until the user clicks the result line.
* Status: open.

**F24. One core thread: a slow request blocks the next with no sign.** `core/src/service.rs`
* `flow.handle` runs on one thread; while Spotify polls (F05), an app launch waits for its process (8 s) or the lock check polls, a new
  submit is queued and the bar shows "Working..." with no queue indicator or cancel (F22).

**F25. The DND script closes the user's Settings window.** `system.dnd`
* `dnd.rs:54` runs `Get-Process SystemSettings | Stop-Process -Force` after toggling, so a Settings window the user already had open is
  killed, losing anything unsaved, and Settings flashes on screen on every call. The decision log records it "never run live".

**F26. "Check" steps that cannot fail.** `browser.*`, `web.*`, `calc.*` (lint L3)
* For these 8 skills `check()` re-parses the request and returns "answerable" (`browser.rs check`, `web_lookup.rs check`,
  `local_calc.rs:107`). It cannot catch an action that did not happen, and the flow reports success regardless. Section 5 lists what each
  skill's check proves. Not a user-visible bug by itself, but it means a "Done" for a page that did not open is possible.

**F27. Calculator gaps with an unhelpful error.** `calc.math`

## 4. Systemic root causes

**S1. Skills hand the whole sentence to the connector as `{request}` and declare no slots.** 18 of 24 shipped skills (lint L2). Slot
validation, the typed `ask:` question (D32b), the resolver's closed lists and per-slot learning therefore apply to only two skills
(`stub.send`, `settings.place`). Every other skill's parsing lives in a connector `parse_*` function that sees a raw, possibly misspelt sentence,
and any missing value can only come back as an error string. This single cause produces F03 (query), F06, F08, F12, F13, F15, F17, F19, F27.

**S2. The connector-to-flow channel can say "done" or "failed", nothing else.** `Connector::execute` returns `Result<Output, ConnError>`; the
flow has `Prompter::choose` and `ask_text`, but a connector cannot use them. So 23 "questions" are rendered as errors. Fix once, benefit everywhere:
add `ConnError::NeedsInput { question, choices, hint }`; the flow shows the choice or the typed field and re-runs the step with the answer appended
(or as a named arg). Timer length (`flow.rs ask_timer_length`) is the one hand-written example of this and should be generalised.

**S3. Verification is a second parse of the same sentence, and it overrides the first answer.** For browser, web and calculator skills `check()` can never fail
(lint L3). For Spotify and lock it polls, then reports "I couldn't confirm" in place of the connector's own accurate message and after the action has already
happened (F05). A verifier should be able to refine the message ("Opened the search; Spotify did not start playing") but not convert a done action into an
error, and it must be bounded in time.

**S4. User-facing strings are borrowed from example data.** Fixed for the confirm and choice text by `title:`. Still borrowed: hint text inside errors
("Try "remind me to call mom at 6pm"", "Say, for example, 'will it rain in Pune tomorrow'", "Try "search YouTube for pasta"", "Try "open Amazon"", "Try
"open MKBHD's latest video""): 43 corpus cases show an example the user never typed. Replace with a question and chips.

**S5. Decisions come from a confidence number, not from what is missing.** `decide()` (`router.rs:44`): below 0.30 -> "I can't do that yet."; 0.30 to 0.50 ->
three skills regardless of relevance; 0.50 to 0.80 -> confirm; a label with no built skill -> decline. There is no "I understood X but not Y" path, no typo
tolerance outside the model, and an unlabeled skill with a placeholder example (`stub.send`) wins at 0.9 against the model.

**S6. Settings and promises live in comments.** `dnd.rs:14` ("the app scheduler must turn DND off") and the `LocalCalc` place source (not wired in
`registry.rs:225`) are contracts between crates that nobody enforces. A test that builds the same connector map as the app and asserts "after `set my city`, sunset
uses it" and "after `dnd for an hour`, a `dnd_off` row exists" would have caught both.

**S7. One thread, no panic isolation, no cancel.** `service.rs:106`. F02, F22, F24.

**S8. UI state drives `disabled`, mount and focus together.** `App.tsx:346`, `showStatus`. F21.

## 6. UI / UX gaps visible from code (`app/src/App.tsx`, `state.ts`)

What the bar shows per phase: idle = input; working = "Working..." (input unmounted); confirm = card (input present but disabled); choice = numbered buttons,
keys 1-9 only; asking = input is the answer field; done / failed = status line, first printable key brings the input back, Backspace clears, Esc closes.

* Focus is lost in five phases (F21). Enter in `confirm` is guarded 400 ms (good).
* No way to stop a running action (F22). No arrow-key navigation in a choice card; more than 9 choices (e.g. stopping many timers) cannot be reached by key.
* A choice or confirm card never times out, and loses its keyboard once the window loses focus (F22).
* `Done` is used for questions (F14) and for refusals that are really failures ("Cancelled." after dismissing a choice is a Done).
* The error line for a failed request closes after 8 s plus reading time; the user's typed text is gone (the line was cleared on send), so a typo means retyping.
* Result text is one line; long messages (`help` 341 chars, screenshot path) overflow.
* Chips (the orb) are four static suggestions, shown only when idle and empty. They are well-formed, but a bare command never offers its own completions (the natural place for
  S2's choices).
* Hint text in the input during `asking` comes from the flow ("For example 7 minutes, or 1h 30m") and is good; the same mechanism is unused by 22 skills.

## 8. The harness

Files added (no product code touched):

| File | What |
|---|---|
| `crates/testset-runner/src/audit.rs` | the engine: corpus parser, fixtures, recording connectors, the script simulator, global rules, reports |
| `crates/testset-runner/src/bin/audit.rs` | the runner (`jitmo-audit`) |
| `crates/testset-runner/tests/audit_smoke.rs` | `cargo test` smoke test (rule-based router only) |
| `testset/audit_corpus.txt` | 643 cases: `skill | kind | input | expectation | note` |
| `crates/testset-runner/Cargo.toml`, `src/lib.rs` | `chrono` dependency, the `[[bin]]`, `pub mod audit` |

**Run it**

```bash
# build (use your own target dir to avoid link locks with another build)
CARGO_TARGET_DIR=/tmp/jitmo-audit cargo build --release -p jitmo-testset-runner --bin jitmo-audit

# the real router + extractor (needs target/release/jitmo-model-worker.exe and models/router, models/ner); about 4 minutes
/tmp/jitmo-audit/release/jitmo-audit --threads 6 --md audit-all.md

# options
#   --worker PATH --models DIR --ner DIR   other model locations
#   --rules-only                           the rule-based router, no models (10 s; skips nothing)
#   --only music.play,reminders.timer      some skills        --kind partial   one kind
#   --verbose                              print every case, not just failures     --strict   exit 1 on any failure
#   --all-skills                           also load whatsapp.send_file (the app does not ship it)
cargo test -p jitmo-testset-runner --test audit_smoke      # 2 tests, no models, 0.1 s
```

It prints the static lints of `skills/*.yaml`, a per-skill table (pass, fail, per kind), the global-rule hit counts, then every failing input with
the expectation and the observed behaviour (router label, confidence, decision, the confirm/choice/question text, each connector call with its
arguments and result, the final message). If the worker or the model folders are missing it prints `SKIPPED ...` and exits 0.

**What is real and what is simulated.** Real: the router and NER model worker, `Flow`, the resolver, policy, the verifier, undo, the reminders and settings
connectors on a throw-away SQLite file, the browser / Spotify / system_controls / DND / local_calc / web_lookup / files connectors. Simulated: PowerShell
(`Sim`) records every script and env value and keeps a small model of volume, brightness, radios, DND, media state and screenshots; HTTP records the URL and
answers "offline"; opening an app and revealing/opening a file only check existence; the clock is Monday 9 Nov 2026, 10:00. Flags in a case's expectation
(`env=nospotify|noplay|stuck|nolink|nobrightness|unlock|dnd_stuck|dnd_missing|city_pune`) switch the simulator into a failure mode to test honesty.

**Expectation words** (`audit.rs parse_expect`): `run:<skill>`, `ask` (a question and nothing executed first), `decline`, `fail:<skill>`, `done`, alternatives with
`/`; modifiers `call=`, `nocall=`, `arg=k~text`, `url~text` / `url!~text` (decoded URL or HTTP request), `msg~` / `msg!~`, `ui~`, `opt~` (a quick-choice option),
`noexec`, `pick=`, `say=`, `env=`, `undo`, `pending=N`. `a && b` sends two requests in a row.

**Global rules applied to every case** (the hit counts in section 1): G0 panic; G1 an example word the user did not type is shown (arijit, mom, pasta, Pune ...);
G2 raw `{placeholder}`; G3 a skill's example sentence shown instead of the request; G4 empty / not one short line; G5 raw system text (PowerShell, exception);
G9 the action ran but the user is told it failed; G10 a question delivered as a failure; G11 bare "Done." for a reminder; G12 connectors block the core thread over 3 s.

**To add a case**, append a line to `testset/audit_corpus.txt` and run with `--only <skill>`. Keep the expectation to the ideal behaviour.

## 9. What this audit did not cover

* Answer correctness of weather and facts (no network by design). The URLs that would be requested are recorded and correct in shape.
* The real PowerShell scripts (UI Automation, Core Audio, WinRT radios, WMI brightness, DND toggling) and real Spotify: the simulator tests the connector's
  decisions and honesty, not whether the scripts work on a given PC.
* Toast delivery (the toast XML asks for the reminder sound, whether it plays was not tested); the app index behind `windows_system`; Explorer selection (`selected_file`), so every file case ran with nothing selected.
* The UI findings F21 to F23 are from reading `App.tsx` and `state.ts`; they were not run in the Tauri window.
* Voice input does not exist yet; "voice-transcription-like" text is approximated by fillers, mishearings (`open spot if i`) and missing spaces.
