# Local Assistant Engine — 00.7 Memory, Personalization and Local Search

7 Nov 2026 · @Ved Narvekar

## Summary

Memory is what lets users say less over time: "send the report to Ved" instead of the full file path, contact and app. It is also what makes search by meaning possible, like "find the doc about the Goa trip budget."

Everything here lives on the laptop, encrypted, and fully visible and editable by the user. Nothing is learned from other people's data, and no sensitive traits are ever guessed.

This doc covers each memory layer, how learning works, the people map, preferences, routines, local search, asking questions about your documents, storage, user control, federated learning, building, testing and edge cases.

## Memory layers

**Memory stays on the laptop, from minutes to as long as you want**

| Layer | What it holds | When |
|---|---|---|
| Short-term context | last 5 requests | v2 |
| Learned defaults and phrases | updated after each task | v1 |
| Facts you ask it to remember | until you delete them | v1 |
| Preferences | set by you or learned | v2 |
| People map | one person across apps | v2 |
| Routines and search index | habits, search by meaning | v2 |
| Federated learning | only anonymous model updates leave | Later |

The layers run from "Minutes" (short-term context) down to "Until you delete" (facts, routines and search index).

Only learned defaults and remembered facts are needed for v1. Every layer above the dashed one (federated learning) stays on the laptop, encrypted.

## What the assistant remembers

| Memory | Example | Comes from | Lasts |
|---|---|---|---|
| Short-term context | "it" = the file just sent | The last few requests | About 5 minutes |
| Learned defaults | "Ved" = Ved on WhatsApp; "the report" = files in /Reports | Successful tasks and the user's choices | Fades if unused |
| Personal phrases | "blast some lofi" = play on Spotify | Successful tasks | Fades if unused |
| Explicit facts | "Remember my manager is Priya" | The user says it | Until deleted |
| Preferences | Short drafts; working hours 9–6 | Settings, or learned from edits | Until changed |
| People map | Rahul Mehta = the same person on WhatsApp, Gmail and Teams | Contacts across apps, confirmed by the user | Until deleted |
| Routines | Every Friday: export report, email manager | Repeated actions in the action log | Until dismissed |
| Search index | Meaning of files, emails and notes | Files and apps the user allows | Rebuilt as things change |

**What it never stores:** message or email contents (beyond the search index the user turned on), audio, screenshots, or guesses about health, religion, politics, sexuality or other sensitive traits.

## How learning works

No model is retrained. Learning is simple counting with fading, stored in the local database. That keeps it fast, explainable and easy to undo.

### Signals

| Signal | Effect |
|---|---|
| Task succeeds | +1 for the choices used (contact, app, folder, phrase) |
| User picks an answer after a question | +2 for that choice: a clear, deliberate signal |
| User corrects a choice ("no, the other Rahul") | −3 for the wrong choice, +2 for the right one |
| User presses Undo | −1 for the choices used |
| User says "remember …" | Saved as an explicit fact, at full strength |
| User says "forget …" | Deleted right away, including anything learned from it |

### Fading

Each learned choice has a score that halves if unused for about 60 days (tuned in beta). Old habits fade, so a new job or a new friend takes over naturally.

### When a default is used

A learned default is used only when it clearly wins, about twice the score of the next choice. Otherwise the assistant asks. Sends always show the default in the confirm card, so a wrong guess is easy to catch.

### What never teaches the assistant

Content in emails, pages or messages never creates defaults on its own. Only the user's own requests and choices do.

## People map (v2)

The same person shows up differently in each app: "Rahul M" on WhatsApp, rahul@company.com in Gmail, "Rahul Mehta" in Teams. The people map joins them into one person.

### How identities are joined

1. **Strong match:** same phone number or same email address across apps. Joined automatically.
2. **Likely match:** very similar names, plus signs like messaging the same group. Suggested to the user: "Are these the same Rahul?"
3. **Never guessed for sends:** a send uses only strong matches or ones the user confirmed.

### What a person record holds

| Field | Example |
|---|---|
| Names and nicknames | Rahul Mehta; "Rahul"; "RM" |
| Identities per app | WhatsApp number, work email, Teams user |
| Usual channel | Usually WhatsApp for quick notes, email for files |
| Labels the user gives | "my manager", "design team" (only if the user says so) |

### What it never holds

No relationship guesses, no personal details from message contents, no sensitive traits. Records are relationship context, not profiles of other people.

## Preferences (v2)

| Preference | Set by | Used for |
|---|---|---|
| Default apps (email, chat, music, browser) | Settings, or learned from use | "message Ved" picks the right app |
| Default folders (downloads, invoices, reports) | Learned from moves and saves | "save the invoices" picks the folder |
| Draft style: length and formality | Settings, or learned from how the user edits drafts before sending | Reply drafts sound like the user |
| Working hours | Settings | No reminders or suggestions outside them; meeting suggestions inside them |
| Spoken replies on or off | Settings | Voice output |
| Confirm level | Settings, within safety rules | Extra confirms for some actions; never fewer than the safety minimum |

Learning draft style compares the assistant's draft with what the user finally sent, only on the device. Only style signals are kept, like "usually shorter," never the message text.

## Routines and suggestions (v2)

### How routines are found

1. **Read the action log** on the device, as a list of task events: skill, main details, day and time.
2. **Find repeated sequences:** the same steps in the same order, like "find report → email manager." A standard sequence-mining method spots patterns that repeat.
3. **Check timing:** does it happen at a regular time, like Friday afternoons?
4. **Threshold:** a pattern must repeat at least 3 times, with similar timing, before it counts.

### How they're offered

- A gentle suggestion: "You often send the weekly report to Priya on Fridays. Make it a shortcut?"
- At most one suggestion per day, never during focus time or outside working hours.
- "No thanks" means that pattern is never suggested again.
- Accepted suggestions become saved shortcuts. Running one on a schedule is a separate choice, and sends still need a confirm.

### Proactive help (later)

Timely nudges built on the same signals, like "Your 3pm starts in 10 minutes. Open the notes?" Off by default, turned on per type of nudge.

## Local search (v2)

v1 finds files by name, type and date through Windows Search. v2 adds search by meaning across files, emails and notes, all on the device.

### What gets indexed

| Source | What's indexed | Opt-in? |
|---|---|---|
| Files in chosen folders | Names, paths and the text inside documents, PDFs, spreadsheets and slides | Yes; user picks folders |
| Emails | Subject, sender, date and body text | Yes, per account |
| Notes apps (later) | Note text | Yes |
| Cloud-only files (OneDrive, Drive placeholders) | Names only; never downloaded just to be indexed | Automatic |

Never indexed by default: system folders, password files, anything in excluded folders the user sets.

### How indexing works

1. **Watch for changes:** Windows file-change notifications tell the indexer what's new or edited.
2. **Pull out text:** small parsers read Word, Excel, PowerPoint and PDF files.
3. **Split into chunks:** long documents are split into short passages, so a match points to the right part.
4. **Turn chunks into numbers:** the same embedding model used for routing turns each chunk into a vector.
5. **Store two indexes:** a vector index (HNSW) for meaning, and a keyword index (Tantivy, a Rust search engine) for exact words.

### How searching works

The query runs on both indexes. Results are merged with a standard method (reciprocal rank fusion), so a file that matches by meaning *and* by keywords ranks highest.

### Keeping it light

- Index only when the laptop is idle and plugged in; pause on battery.
- Low CPU priority; never more than one core.
- Size cap for the index, with oldest or least-opened items dropped first.
- The index is encrypted like all local data.

## Ask about your documents (v2)

Examples: "Summarize this PDF," "What did the contract say about the notice period?", "What's the total in the March invoice?"

### How it works

1. **Find the right passages:** local search returns the top few chunks from the chosen file, or from all indexed files.
2. **Answer from them only:** the 1–3B model gets the question and those passages, with a rule to answer only from them.
3. **Show sources:** the answer names the file and the part it came from, with a link to open it.
4. **Say when it doesn't know:** if the passages don't contain the answer, it says so rather than guessing.

### Limits to be honest about

- A 1–3B model handles short, factual questions well. Long, complex reasoning across many documents is weaker.
- Very long files are summarized section by section, then combined.
- Numbers in tables are read by plain code where possible, not by the model, to avoid mistakes.

## Storage design

These tables extend the ones in doc 07, in the same encrypted SQLite file. The vector and keyword indexes are separate encrypted files next to it.

```sql
-- One row per real person (v2)
CREATE TABLE people (
  id INTEGER PRIMARY KEY,
  display_name TEXT NOT NULL,
  labels TEXT,            -- only labels the user gave, e.g. "my manager"
  created_at TEXT NOT NULL
);

-- Each app identity linked to a person
CREATE TABLE identities (
  id INTEGER PRIMARY KEY,
  person_id INTEGER REFERENCES people(id),
  app TEXT NOT NULL,          -- whatsapp | gmail | teams ...
  handle TEXT NOT NULL,       -- number, email or user ID
  confirmed INTEGER DEFAULT 0 -- 1 if strong match or user confirmed
);

-- Learned choices with fading scores (extends defaults in 07)
CREATE TABLE learned (
  id INTEGER PRIMARY KEY,
  kind TEXT NOT NULL,         -- contact | app | folder | phrase
  phrase TEXT NOT NULL,
  context TEXT,
  value TEXT NOT NULL,
  score REAL NOT NULL,
  last_used TEXT NOT NULL
);

-- Facts the user asked to remember
CREATE TABLE facts (
  id INTEGER PRIMARY KEY,
  text TEXT NOT NULL,
  created_at TEXT NOT NULL
);

-- Routine ideas and the user's answer (v2)
CREATE TABLE routines (
  id INTEGER PRIMARY KEY,
  steps TEXT NOT NULL,        -- list of skill IDs and details
  schedule_hint TEXT,         -- e.g. "Fri afternoon"
  status TEXT NOT NULL        -- suggested | accepted | dismissed
);

-- What's in the search index (v2)
CREATE TABLE index_items (
  id INTEGER PRIMARY KEY,
  source TEXT NOT NULL,       -- file | email | note
  ref TEXT NOT NULL,          -- path or message ID
  modified_at TEXT NOT NULL,
  chunk_count INTEGER
);
```

## User control and privacy rules

| Control | What it does | When |
|---|---|---|
| "What I've learned" panel | Lists every learned choice, fact, person link and routine, in plain words | v1 |
| Edit or delete any item | Takes effect immediately | v1 |
| "Forget [person or thing]" | Deletes it and everything learned from it | v1 |
| Pause learning | Stops new learning; existing memory still works | v1 |
| Search sources | Choose folders and accounts to index; exclude any folder | v2 |
| Export my memory | Download everything as a readable file | v2 |
| Delete everything | Wipes all memory and the search index | v1 |

**Rules that never change:**

- No guesses about sensitive traits: health, religion, politics, sexuality, ethnicity or finances.
- No memory about other people beyond the people map's contact details and user-given labels.
- Memory never leaves the laptop, except encrypted sync the user turns on (v2).
- Each Windows user account has its own separate memory.

## Federated learning (later)

Personal memory makes the assistant better for one user. Federated learning makes the shared models better for everyone, without collecting anyone's data.

### How it works

1. Our server sends the current shared model, like the router's fine-tuned head, to opted-in devices.
2. Each device trains a small update on its own personal phrases, when idle and plugged in.
3. Devices send back only the weight changes, never phrases or data.
4. The server combines many updates into a better shared model, tests it, and ships it if it beats the current one.

### Privacy protections

| Protection | What it does |
|---|---|
| Secure aggregation | The server only ever sees the sum of many updates, never one device's update |
| Differential privacy | Each update is clipped and gets added noise, so no single user can be worked out from the result |
| Minimum group size | No round runs with too few devices |
| Opt-in only | Off by default; clearly explained |
| Separate pools for teams | A company's updates stay in its own pool, unless it chooses to join the global one |

### What gets federated

Only small shared models: the router and the extractor. Personal memory, the people map and the search index never leave the laptop.

### When

Only once there are enough active users for it to help. Until then, offline fine-tuning (doc 00.5) improves the models more cheaply.

## How we build it

### Modules (Rust, in the core engine)

| Module | Job | Libraries | When |
|---|---|---|---|
| `memory` | Learned choices, facts, fading, signals | SQLite (SQLCipher) | v1 |
| `memory_ui` | The "What I've learned" panel and forget actions | Tauri UI | v1 |
| `people` | Joining identities into people | SQLite; string matching from doc 00.3 | v2 |
| `prefs` | Preferences, including draft style signals | SQLite | v2 |
| `routines` | Sequence mining over the action log; suggestion rules | Own Rust code | v2 |
| `indexer` | File watching, text extraction, chunking, embedding | Windows file notifications; document parsers; the embedding model | v2 |
| `search` | Vector and keyword search, merged results | An HNSW library; Tantivy | v2 |
| `doc_qa` | Answering from documents with sources | Search + the 1–3B model | v2 |
| `federated` | On-device updates and secure upload | To be chosen; possibly an existing federated learning library | Later |

### Build order

1. `memory` and `memory_ui`, in v1 alongside the resolver.
2. `people` and `prefs`, early in v2.
3. `indexer` and `search`, then `doc_qa`.
4. `routines`, once enough real action logs exist from beta users.
5. `federated`, once the user base is large enough.

## How we test it

| Test | What it measures | Target |
|---|---|---|
| Simulated month of use | Scripted user runs 30 days of tasks; count questions asked per week | Questions drop by half or more by week 4 |
| Wrong-default rate | How often a learned default is wrong and gets corrected | Under 2% |
| Forget test | After "forget X", nothing about X remains in any table or index | 100% |
| Search relevance | Ranking quality on a test folder of 1,000 files with known right answers (nDCG@10, a standard search score) | Clearly better than name-only search |
| Indexing load | CPU, memory and battery while indexing | Pauses on battery; one core max; no user-visible slowdown |
| Document answers | Correct answers with correct sources on a question set; says "not found" when it should | 90%+ correct; no made-up answers |
| Routine suggestions | Share of suggestions users accept in beta | Over 30%, or suggestions get stricter |
| Sensitive-trait check | No stored item guesses a sensitive trait | 100% |

## Edge cases

| Case | How it's handled |
|---|---|
| Shared laptop, several Windows users | Each Windows account has its own memory and index |
| Two friends with the same name | Kept as separate people; asks which one, then learns |
| Contact changes number or email | Strong match on the other identity keeps the person; asks to confirm the new detail |
| A learned default goes stale (new manager) | Fading lowers it; a correction replaces it at once |
| Wrong default used once | Correction gives it a strong negative score, so it's rarely repeated |
| Huge drives or folders | Only chosen folders; size cap; newest and most-opened first |
| Locked or encrypted files | Skipped and listed in settings as "couldn't index" |
| Cloud-only files | Name only; never downloaded just to index |
| User deletes a file | Removed from the index on the next change notice |
| Memory grows very large | Old, low-score items are trimmed automatically |
| New laptop | Memory starts fresh, unless encrypted sync is on (v2) |
