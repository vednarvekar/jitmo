# Local Assistant Engine — 00.9 Output and Accessibility

7 Nov 2026 · @Ved Narvekar

## Summary

Output is how the assistant talks back: result lines, confirm cards, notifications, spoken replies and, later, highlights on screen. The rule is simple: say what happened, in as few words as possible, using the quietest surface that does the job.

Accessibility is part of the same design. An assistant that does clicks for you can change daily life for people with limited mobility or vision. So every screen works by keyboard alone and with screen readers, and voice-only use becomes possible in v2.

This doc covers attention levels, every output surface, writing rules, notifications, spoken replies, the daily view, on-screen highlights, visual design, accessibility standards and features, languages, building and testing.

## Attention levels

**Each message uses the quietest surface that does the job**

| Surface | What it is | Level |
|---|---|---|
| Action log | always written, never interrupts | Quietest |
| Tray badge | something needs a look | ↓ Go down only when needed |
| Result line | one line after each task | ↓ |
| Notification | reminders, alerts, failures | ↓ |
| Spoken reply (v2) | only when you spoke first | ↓ |
| Confirm card | nothing sends without it | Needs your action |

Most messages stop at the result line. Only sends and shares reach the bottom rung, where the user must choose.

## Output surfaces in detail

| Surface | What it shows | How long it stays | When |
|---|---|---|---|
| Result line | One line under the bar: "Playing Arijit Singh on Spotify" | Until the bar closes, about 3 seconds | v1 |
| Confirm card | Who, what and where, with Send, Edit, Cancel | Until the user chooses | v1 |
| Question chips | One short question with 2–3 answers | Until answered or closed | v1 |
| Undo toast | "Moved 4 PDFs. Undo" | 10 seconds | v1 |
| Progress list | Steps of a chained request, ticking off | Until done | v1 |
| Info card | Short results that need more than a line: urgent emails, today's schedule, search results | Until closed; clickable items | v1 |
| Notification | Reminders, automation alerts, failures | Follows Windows notification rules | v1 |
| Tray badge | A small dot when something needs attention | Until seen | v1 |
| Action log | Everything that happened | Per retention setting | v1 |
| Spoken reply | Short result read aloud | Spoken once | v2 |
| Daily view | Today's schedule, follow-ups, suggestions | Opens on request or at a set time | v2 |
| On-screen highlight | A glow around what the assistant clicked | While acting | Later |

## Writing rules

Every word the assistant shows or speaks follows these rules.

| Rule | Good | Bad |
|---|---|---|
| Say what happened, in past tense | "Sent to Ved on WhatsApp." | "I'm happy to let you know your message was sent!" |
| One line where possible | "Moved 4 PDFs to Invoices." | A paragraph explaining the move |
| Failures: what happened + what to do | "Gmail needs you to sign in again." + Sign in button | "Error 401: unauthorized" |
| Plain words, no jargon | "No internet right now." | "Network request timed out." |
| Exact names and numbers | "Q3_report.pdf to Rahul Mehta" | "the file to your contact" |
| Calm, not chatty | "Done." | "Awesome! All done for you!" |
| Honest when unsure | "The file may not have sent. Please check WhatsApp." | "Sent!" when it isn't confirmed |
| Never blame the user | "I didn't get that. Did you mean…" | "Invalid command." |

All text lives in a string catalog, not inside code, so it can be reviewed in one place and translated later.

## Notifications

Notifications interrupt people, so they're used sparingly and always respect Windows Focus and Do Not Disturb.

| Category | Example | Default | Buttons |
|---|---|---|---|
| Reminders and timers | "Call mom" | On, always | Snooze, Done |
| Automation sends | "Friday report sent to Priya" | On | Open, Undo where possible |
| Automation needs a confirm | "Send this week's report?" | On | Send, Skip |
| Failures | "WhatsApp isn't open; the send didn't happen" | On | Fix, Open |
| Suggestions (v2) | "Make Friday report a shortcut?" | On, at most one a day | Yes, No thanks |
| Proactive nudges (later) | "Your 3pm starts in 10 minutes" | Off | Open notes, Dismiss |

**Rules:**

- **Respect focus:** only reminders the user set themselves break through Focus or Do Not Disturb.
- **Group them:** several alerts from one automation become one notification.
- **Cap them:** no more than a few non-reminder notifications per hour.
- **Control:** each category can be turned off in settings.
- **Private on lock screen:** message content is hidden on the lock screen by default.

## Spoken replies (v2)

| Topic | Rule |
|---|---|
| When it speaks | Only when the user spoke the request, or in voice-only mode. Typed requests get text replies. |
| Length | One short sentence, like "Sent to Ved." Longer results show on screen, with "I've put the details on screen." |
| Confirms | Read aloud in voice-only mode: "Send report.pdf to Ved on WhatsApp. Say send or cancel." |
| Stopping | Pressing any key, or saying "stop," stops speech at once |
| Private content | Message and email contents are not read aloud unless the user turns that on, since others may be nearby |
| Names | Users can fix how a name is pronounced, once, in settings |
| Voice and speed | A few voices to choose from; adjustable speed |
| Engine | Piper or Kokoro on the device (doc 00.2); speech starts within about half a second |

## Daily view and morning brief

**v1, morning brief:** typing "morning brief" shows an info card with urgent emails and today's meetings. Each item is clickable.

**v2, daily view:** a small panel the user opens with a hotkey, or that appears at a chosen time.

| Section | Content |
|---|---|
| Today | Meetings, with join links and prep notes (C3) |
| Needs a reply | Emails and messages waiting for the user (E4) |
| Reminders | Due today |
| Automations | What ran, and anything that needs attention |
| Suggestions | At most one helpful idea |

**Rules:** it loads in under a second from local data, shows only what's useful today, and every item links to a one-click action like Reply, Join or Open.

## On-screen highlights and show-me mode (later)

**Highlights:** when the assistant works inside an app through the accessibility tree, a soft glow appears around each element it uses, like the WhatsApp Send button. Users can see what it's doing, and spot problems.

**Show-me mode:** "Show me how to turn on Bluetooth." Instead of doing it, the assistant highlights each step for the user to click. Useful for learning, and for people who prefer to stay in control.

**How it's built:** a transparent, click-through overlay window drawn on top of the screen, using element positions from UI Automation. It never captures the screen.

## Visual design rules

| Area | Rule |
|---|---|
| Look and feel | Feels native to Windows 11: the system font (Segoe UI Variable), rounded corners, soft shadows |
| Themes | Follows Windows light, dark and high-contrast modes automatically |
| Text size | Follows Windows text-size and scaling settings, up to 200% and beyond without clipping |
| Color | Never the only signal; icons and words carry meaning too. Text contrast at least 4.5 to 1 |
| Motion | Short, simple animations; none when Windows "reduce animations" is on |
| Size and position | Quick bar opens on the screen the user is working on, centered near the top; remembers its size |
| Icons | Each app's real icon on confirm cards, so the destination is obvious |
| Density | Plenty of space; one main action per card, clearly marked |

## Accessibility standards for our own screens

Target: WCAG 2.2 level AA, the widely used accessibility standard, for every screen in the app.

| Need | How we meet it |
|---|---|
| Keyboard only | Every action has a key; visible focus outline; logical tab order; no keyboard traps |
| Screen readers (Narrator, NVDA, JAWS) | Every control has a clear name and role. If the UI uses Tauri's web view, standard web accessibility markup is exposed to Windows screen readers. A native UI uses Windows accessibility directly |
| Live results | Result lines and alerts are announced automatically to screen readers, without moving focus |
| Confirm cards | Read in a fixed order: action, recipient, content, buttons |
| Contrast and size | 4.5 to 1 text contrast; click targets at least 24 by 24 pixels |
| Time limits | The Undo toast pauses while focused; no action depends on acting fast |
| Errors | Described in words, with a fix, and announced |

## Accessibility as a feature

Beyond making our own screens accessible, the assistant itself can remove barriers in other apps.

| Group | How the assistant helps | When |
|---|---|---|
| Limited hand mobility | One typed or spoken line replaces many clicks and drags across apps | v1 typed; v2 voice |
| Blind or low vision | Voice-only mode: speak requests, hear results and confirms; avoids hard-to-reach buttons in other apps | v2 |
| Low vision | Large text, high contrast, and results read aloud on request | v1 and v2 |
| Dyslexia or typing difficulty | Typo tolerance and voice input | v1 and v2 |
| Cognitive load | Plain language, one step at a time, confirms read back, Undo everywhere | v1 |

We test with people from these groups, ideally through partner disability organizations, before each major release.

## Languages and localization

v1 is English only, but it's built so other languages can be added without rewriting screens.

| Design now (v1) | Added later |
|---|---|
| All text in a string catalog, using a localization system like Fluent, which handles plurals and grammar per language | Translations, starting with Hindi |
| Dates, times and numbers formatted by the user's Windows region | Right-to-left layouts, like Arabic |
| Layouts that stretch for longer words | Spoken replies in each language |
| No text inside images | Understanding requests in each language (doc 00.3) |

## How we build it

| Part | How | When |
|---|---|---|
| Quick bar, cards, chips, toasts, main window | UI framework chosen in SP8 (Tauri + React, or native Rust UI); one shared set of components | v1 |
| String catalog | Fluent files, loaded by the core and the UI | v1 |
| Windows notifications | Windows notification APIs through the `windows` crate; registered app ID from the installer | v1 |
| Tray icon and badge | Windows tray APIs | v1 |
| Spoken replies | Text-to-speech in the model worker (doc 00.5); audio out through `cpal` | v2 |
| Daily view | A second window, built from the same components | v2 |
| Highlights overlay | Transparent, click-through, always-on-top window using UI Automation positions | Later |
| Accessibility tooling | Automated checks (like axe-core for web UI) in every build; Microsoft's Accessibility Insights for manual checks | v1 |

One UI engineer owns all of this, as in doc 08, with design help for the visual system.

## How we test it

| Test | What it checks | When |
|---|---|---|
| Automated accessibility checks | Missing labels, contrast, roles, focus order | Every build |
| Keyboard-only run | The full 04 test set done without a mouse | Every release |
| Screen reader run | Main flows with Narrator and NVDA | Every release |
| Scaling and themes | 100–200% scaling; light, dark and high contrast | Every release |
| Writing review | All new strings checked against the writing rules | Every change to the catalog |
| Notification limits | Many events at once stay grouped and capped | Weekly |
| Speech timing | Spoken replies start within about half a second (v2) | Every release |
| Usability with disabled users | Real tasks with people from the groups above | Before beta and each major release |
