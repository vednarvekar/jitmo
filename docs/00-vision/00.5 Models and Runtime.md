# Local Assistant Engine — 00.5 Models and Runtime

6 Nov 2026 · @Ved Narvekar

## Summary

The product uses about eight small open-source models: for understanding, planning, voice and, later, the screen. None is trained from scratch. They all run on the laptop inside one separate process, the model worker, under a 2GB memory budget.

The secret to fitting on 8GB is simple: only the tiny models stay loaded. The bigger ones load the moment they're needed and leave when they're not.

This doc covers every model, the engines that run them, how they're shrunk, how the scheduler decides what to load, speed tricks, GPU and NPU use, battery, downloads and updates, licenses, fine-tuning, security, building and testing.

## Runtimes

A runtime is the engine that actually runs a model file. We aim for one or two, and use at most three, all open source and written in C or C++ for speed.

| Runtime | Runs | Why | File format |
|---|---|---|---|
| llama.cpp | The planner; possibly the embedding model; later the vision model | Best-in-class speed for small language models on CPUs; supports 4-bit models, grammars, adapters and GPUs | GGUF |
| ONNX Runtime | GLiNER, voice detection, text-to-speech; possibly the embedding model | Runs many model types; Microsoft-backed; plugs into GPUs and NPUs on Windows | ONNX |
| whisper.cpp | Speech-to-text, if Whisper wins the voice spike | Same family as llama.cpp; very efficient for Whisper | GGUF (ggml) |

**Where they run:** inside the model worker, a separate process with no network access. The core engine sends it small requests over local IPC, like "embed this sentence" or "plan with these 5 skills," and gets results back.

Fewer runtimes is better: each one adds memory and maintenance. If SP1 shows the embedding model runs well in llama.cpp, and Moonshine wins the voice spike (it runs in ONNX Runtime), we drop whisper.cpp and use only two.

## Quantization

**What it is:** a model is billions of numbers. Normally each is stored in 16 bits. Quantization stores them in fewer bits, like 8 or 4, using clever rounding. The file and memory shrink by half to three-quarters, and the model runs faster on a CPU, with only a small loss in quality.

| Model type | Format we use | Size vs. original | Quality loss |
|---|---|---|---|
| Embedding and extraction (small encoders) | 8-bit (int8) | About half | Usually very small |
| Planner (1–3B) | 4- or 5-bit GGUF, like Q4_K_M or Q5_K_M | About a quarter to a third | Small; Q5 keeps a bit more quality than… |
| Speech-to-text | 5- or 8-bit | About a third to a half | Small for short commands |

**How we choose:** for each model, test two or three quantization levels on our own test sets. Pick the smallest one that stays within 1–2 points of the original's accuracy.

## How the scheduler decides

The scheduler is plain Rust code in the core engine. Its job: keep the right models ready while staying under budget.

### The budget

Budget = the smaller of 2GB, or free RAM minus a 1GB safety margin. On a busy 8GB laptop with Chrome open, that might be only 1.2GB, and the scheduler adapts.

### Priority order

1. **Pinned:** the embedding model and extractor. Never unloaded while the app runs.
2. **Active:** whatever the current request needs right now.
3. **Warm:** recently used models, kept loaded until their idle timer runs out.
4. **Cold:** everything else, on disk only.

### Rules

- **Idle timers:** planner unloads after about 2 minutes unused; voice models after about 5. Tuned in SP8.
- **One big model at a time:** the planner and the vision model never load together. A second big request waits in a queue.
- **Least recently used goes first** when space is needed.
- **Prefetch:** when the router sees a chained request coming, the planner starts loading while extraction runs. When the voice key is pressed, voice models start loading immediately.
- **Memory pressure:** Windows can signal when memory runs low. The scheduler then unloads warm models at once.
- **Doesn't fit:** if a model can't fit even after unloading, the request is declined with "I can't plan that right now," never crashing.

### Why reloads are fast

Model files are opened with memory mapping. Windows keeps recently read files in its cache, so a model unloaded a minute ago often reloads from RAM in a fraction of a second, not from disk.

## Speed tricks

| Trick | What it does | Saves |
|---|---|---|
| Prompt caching | The planner's fixed rules are processed once and saved. Each request only adds its own short part. | Often a large share of planner time |
| Short prompts | Only the top 5 skills are shown, as one-line signatures | Fewer words to read means faster answers |
| Short answers | Plans are capped at 5 steps; summaries at a few sentences | Generation time grows with length |
| Grammar-shaped output | The final plan can only be valid JSON, so no retries for broken output | Retry time |
| Right thread count | Use the CPU's real cores, not virtual ones, for model math | Avoids slowdowns from oversubscribing the CPU |
| Warm-up | Run one tiny request right after loading | First real request isn't slow |
| Lower priority when idle | Background work runs at below-normal CPU priority | The user's own apps stay smooth |
| Templates and plan cache | Most chains never reach the planner at all (doc 00.3) | The full planner cost |

## GPU and NPU acceleration (v2)

v1 runs everything on the CPU, so it works on every laptop. v2 adds faster paths when a laptop has extra AI hardware. The CPU path always stays as the fallback.

| Hardware | How we use it |
|---|---|
| Any GPU, including built-in graphics | llama.cpp's Vulkan support; ONNX Runtime's DirectML support |
| NVIDIA GPUs | llama.cpp's CUDA support |
| Qualcomm Snapdragon NPUs | ONNX Runtime's Qualcomm (QNN) support; needs the ARM build from doc 00.1 |
| Intel Core Ultra NPUs and GPUs | ONNX Runtime's OpenVINO support |
| AMD Ryzen AI NPUs | ONNX Runtime's AMD support |

Microsoft's Windows ML aims to pick these automatically on Windows (to verify how mature it is by v2).

**Detection:** on first run, the app checks which hardware is present, runs a short speed test on each path, and picks the fastest one that passes an accuracy check.

**Watch out for:** NPUs often support only some model types. Each model is tested on each path before it's allowed to use it.

## Battery and heat

Laptop users notice a hot laptop or a draining battery fast. Rules:

- **Idle means idle:** no model runs unless the user asked for something. Target: under 1% CPU.
- **On battery:** fewer CPU threads for models, shorter idle timers, no prefetching.
- **Battery saver on:** only pinned tiny models stay loaded; the planner loads only when truly needed.
- **Short bursts only:** model work comes in short bursts of a few seconds, so fans rarely spin up.
- **Measure it:** battery drain per hour of normal use is tested every release (see How we test it).

## Packaging, downloads and model updates

### Model registry

The update server keeps a signed list of every model the app may use:

```yaml
  version: 3
  file: minilm-l6-v2.q8.gguf
  size_mb: 25
  sha256: "9f2c..."          # checked after download
  license: apache-2.0
  min_app_version: 1.0.0
  rollout_percent: 100       # staged rollouts start lower
```

### Download order on first run

1. Embedding model and extractor first, so known tasks work within the first minute.
2. Planner model next, in the background.
3. Voice models only when the user turns voice on (v2).

### Rules

- **Resumable downloads:** a dropped connection continues where it stopped.
- **Verified:** each file's fingerprint (SHA-256) and signature are checked before it's used.
- **Staged rollout:** a new model goes to 5% of users first, then more if failure rates stay normal.
- **Rollback:** the previous version is kept until the new one proves stable.
- **Location:** the user's local app data folder; no admin rights needed.
- **Disk check:** warn before downloading if free space is low.

## Choosing and re-checking models

New open-source small models come out every few months, often clearly better. So model choice is a repeating process, not a one-time pick.

1. **Shortlist:** 2–4 candidates per job, from trusted publishers.
2. **License check:** drop any that don't allow commercial use (see Licenses).
3. **Test on our sets:** accuracy on the doc 00.3 test sets, plus speed and peak memory on the 8GB test laptop.
4. **Pick:** the best accuracy that meets the speed and memory budgets.
5. **Re-check every quarter:** test new releases the same way. Switch only if clearly better, since every switch needs a full test run and a staged rollout.

## Fine-tuning, only when needed

If an off-the-shelf model misses its target in a spike, we adapt it rather than replace it. No own hardware is needed.

| Model | Method | Where it runs | Output |
|---|---|---|---|
| Embedding model (routing) | SetFit, using a few examples per task | A laptop or a cheap rented GPU, in minutes | A new small model file |
| GLiNER (extraction) | Fine-tune on labeled example requests | One rented GPU, a few hours | A new model file |
| Planner | LoRA adapter, which trains a small add-on instead of the whole model | One rented GPU, a few hours | An adapter of tens of MB |
| Speech-to-text | LoRA on recorded commands with accents | One rented GPU | An adapter or merged model |

Steps: build training data (test-set wording plus reviewed examples from a large model) → train → convert and quantize → test on the same sets as before → ship only if clearly better → staged rollout.

Data rule: training never uses real user content. Users' own phrasings stay on their devices as personal examples (doc 00.3).

## Optional cloud model (later)

For rare tasks the local planner can't handle. It is never needed for the core product, and it is off by default.

| Rule | Detail |
|---|---|
| Who turns it on | The user, or the admin on Team plans |
| What it's used for | Only planning hard chained requests, never routine tasks |
| What it sees | The request and skill list; personal details like names and file contents are removed or replaced with placeholders first |
| Asking each time | "This needs the cloud model. Send?" unless the user chose "always allow" |
| Cost | Charged per use, or included in a higher plan, since it costs us per request |
| Design now | The planner talks to models through one interface, so a cloud model can plug in later without engine changes |

## Model security

| Risk | Protection |
|---|---|
| A tampered model file | Every file is signed and its fingerprint checked before loading |
| Model formats that can run hidden code | Only safe formats are allowed: GGUF, ONNX and safetensors. Never Python pickle files, which can contain code. |
| A model trying to reach the internet | The model worker process has no network access |
| A model producing a harmful action | Models only suggest; the plan checks and policy engine (plain code) decide what runs, as in docs 07 and 00.3 |
| Trick instructions inside content | Content is marked as data before reaching any model, and can never start an action |
| A model crashing or using too much memory | Separate process, restarted by the core engine; memory budget enforced |

## How we build it

### Modules

| Module | Lives in | Job |
|---|---|---|
| `model_worker` | Separate Rust process | Hosts the runtimes; answers embed, extract, plan, transcribe and speak requests |
| `runtime_llama` | Model worker | Rust bindings to llama.cpp: loading, prompt cache, grammars, adapters |
| `runtime_onnx` | Model worker | The `ort` crate for ONNX Runtime models |
| `runtime_whisper` | Model worker | Rust bindings to whisper.cpp, if Whisper wins the voice spike |
| `scheduler` | Core engine | Budget, priorities, timers, prefetch, memory-pressure handling |
| `registry` | Core engine | Reads the signed model list; knows what's installed and what's current |
| `downloader` | Core engine | Resumable, verified downloads and staged updates |
| `hw_detect` (v2) | Core engine | Finds GPUs and NPUs and picks the fastest safe path |

### Build order

1. `model_worker` with ONNX Runtime and the embedding model; IPC to the core engine.
2. `registry` and `downloader`.
3. `scheduler` with pinned models only.
4. `runtime_llama` and the planner; scheduler timers and prefetch.
5. Speed tricks: prompt cache, thread tuning, warm-up.
6. Voice runtimes (v2); then `hw_detect` (v2).

Rough effort: one ML engineer and the Rust core engineer, about 6–8 weeks for steps 1–5, overlapping with spikes SP1–SP4 and SP8.

## How we test it

| Test | What it measures | Pass rule | When |
|---|---|---|---|
| Speed benchmark | Time per stage and per model on the 8GB laptop | Within the budgets in 00.3 and 03 | Nightly |
| Memory benchmark | Peak and idle memory in each situation | Idle under 300MB; peak under 2GB | Nightly |
| Busy-laptop test | Same, with Chrome, Teams and a video call running | No crash; graceful "can't right now" if short of memory | Weekly |
| 24-hour soak | Memory over a full day of idle plus occasional requests | No growth over time (no leaks) | Weekly |
| Battery test | Drain per hour of normal use | Small compared with the laptop's normal idle drain | Every release |
| Accuracy after quantization | Test-set scores for each shrunk model | Within 1–2 points of the original | Every model change |
| Download test | Interrupted downloads, wrong fingerprints, low disk | Resumes; rejects bad files; warns clearly | Every release |
| Hardware paths (v2) | Each GPU or NPU path vs. CPU | Same answers, faster | Every model change |

Any slowdown over 10% compared with the last release blocks the release until explained.
