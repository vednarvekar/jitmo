# Local Assistant Engine — 00.11 Developer Platform

7 Nov 2026 · @Ved Narvekar

## Summary

No single team can build skills for every app in the world. Outside developers can. The developer platform is how the assistant grows from 49 tasks to thousands, and it's a long-term moat: the more skills exist, the more useful the assistant becomes, and the harder it is to copy.

Developers can extend it six ways, from no-code recipes to full plugins in any language. Every extension runs under the same rules: sandboxed, with declared capabilities, and with confirms for anything that sends.

This doc covers who builds, each extension type, the skill format, WASM plugins, the connector toolkit, MCP, the local API, developer tools, the marketplace, review and publishing, versions, terms, building and testing.

## Skill files: the public format

The same YAML format our own skills use (doc 07), published with a full specification, including the capabilities, limits and category fields (see [07 LLD, Capabilities](../02-design/7%20-%20Low-Level%20Design.md)).

```yaml
format: skill/1                # format version
id: acme.invoices.save         # developer.namespace.name
name: Save invoices to Finance
category: files
version: 1.2.0
examples:
  - "save the invoices from this email"
  - "put these bills in finance"
slots:
  email: { type: email_ref, resolve: [open_email] }
steps:
  - connector: gmail
    action: list_attachments
    args: { email: "{email}", type: pdf }
  - plugin: acme.invoice-parser      # optional WASM plugin for custom logic
    action: name_files
  - connector: files
    action: save
    args: { folder: "Finance" }
check: { connector: files, action: exists, args: { folder: "Finance" } }
capabilities: [gmail.read:attachments, files.write:folder:Finance]
risk: changes_data
undo: delete_saved_copies
```

A free validator checks any skill file before publishing: valid fields, narrow capabilities, required checks, and a confirm for any send.

## WASM plugins: how they work inside

### The contract (WIT)

What a plugin can call, and what it must offer, is written in WIT, WebAssembly's interface language. The host (our app) provides functions; the plugin exports its own.

```wit
package assistant:plugin@1.0.0;

interface host {
  // Only works if the capability is declared and granted
  http-request: func(req: request) -> result<response, error>;
  read-file: func(handle: file-handle) -> result<list<u8>, error>;
  embed: func(text: string) -> list<f32>;          // uses our local model
  request-confirm: func(card: confirm-card) -> bool; // core draws the card
  notify: func(message: string);
}

world skill-plugin {
  import host;
  export run: func(action: string, input: string) -> result<string, error>;
}
```

### Key design choices

| Choice | Why |
|---|---|
| Host holds the tokens | Plugins never see app sign-in tokens. The host adds them to approved requests, so a plugin can't steal them. |
| File handles, not paths | A plugin gets a handle to the one file it was given, never free access to the disk |
| Network only to declared hosts | `http-request` only reaches domains listed in the manifest, through the egress gate |
| Models through the host | Plugins call our local models (embed, extract, summarize) instead of bundling their own; keeps memory low |
| Core draws confirms | `request-confirm` asks the core; plugins can't draw their own buttons |
| Limits per call | CPU budget (fuel), time limit and memory cap, set by Wasmtime |

### WASM ideas and the architecture

The full list of WebAssembly ideas we borrow (sandbox, capabilities, typed interfaces, fuel and deadlines, hot loading, streaming on demand, shared browser code, deterministic replay) is in [6.1 Tech Stack, plugin sandbox](../02-design/6.1%20-%20Tech%20Stack.md). The architecture diagram, with plugins reaching the core only through the capability gate, is in [06 HLD, Plugin host](../02-design/6%20-%20High-Level%20Design.md).

### Languages

Rust has the most mature tooling. Python, JavaScript, Go and C# can also build WASM components, through tools like componentize-py, jco, TinyGo and componentize-dotnet. Their maturity varies, so we test each before officially supporting it.

## Connector toolkit (later)

Lets developers, especially app makers, add support for a new app.

| Piece | What developers get |
|---|---|
| Connector interface in WIT | The same actions, health, execute, check and undo functions our own connectors use (doc 07) |
| Sign-in helper | Declare the app's OAuth details; the host runs the sign-in flow and keeps the tokens |
| API helper | Make approved web requests with the user's token added by the host |
| Accessibility helper | For desktop apps without APIs: find and press elements using selector packs, through host functions |
| Deep-link helper | Open the app at the right place |
| Undo store | Save what's needed to reverse an action |
| Test kit | Fake accounts, recorded API answers and a scripted app for automated tests |

App makers who build an official connector get a "By [app maker]" badge and can be featured in the marketplace.

## MCP: both directions

### Using MCP tools (v2)

**What MCP is:** the Model Context Protocol is an open standard that lets AI assistants use tools through small "servers." Many companies and developers already publish MCP servers for their apps. Supporting it gives us access to a large tool ecosystem without writing each connector ourselves. It also makes the assistant useful to developers who already build MCP servers for other AI tools.

| Topic | Plan |
|---|---|
| How it connects | The core engine acts as an MCP client; local MCP servers run as separate processes on the laptop |
| How tools appear | Each MCP tool becomes a skill: its name and description become routing examples; its inputs become slots |
| Safety | MCP servers are treated as untrusted: capability limits, confirms for any tool that sends or changes things, and tool outputs treated as data, never as commands |
| Local first | Local MCP servers are preferred; remote ones follow the same rules as web lookups and need user approval |
| Quality | Popular MCP tools can be reviewed and marked Verified, like skills |
| When | v2, alongside the plugin host |

### Offering our skills to other AI apps (later, to decide)

The assistant could also act as an MCP server, so other AI apps on the same laptop can use its skills, like "send this file on WhatsApp."

| Benefit | Risk | Safeguard |
|---|---|---|
| Other AI apps can drive the user's laptop through our safe, tested skills | Another app could send without the user knowing | Every send still shows our own confirm card; the user approves each connecting app once |
| Reach users who already live in other AI apps | Trick instructions coming from the other app | Requests from other apps are treated like content-origin requests: no recipients from them without a confirm |
| Positions us as the safe action layer on the PC | Support burden | Start with read-only and safe skills first |

## Local API and command line (v2)

For scripts, launchers and devices like Stream Deck. Covered at product level in doc 00.1; developer details here.

```
# Command line
assistant run "move today's downloads to Bills"
assistant run --dry-run "send the weekly report to Priya"
assistant recipes run friday-report
assistant skills list --category files
```

| Topic | Plan |
|---|---|
| Transport | A local-only connection (named pipe or localhost); never reachable from the network |
| Auth | Tokens created in settings, each with scopes like `run:safe`, `run:all`, `read:log`; revocable |
| Results | JSON output with status, steps done and any confirm still waiting |
| Confirms | Sends still show the confirm card in the app; scripts wait for the answer |
| Rate limits | Same limits as typed requests |
| Logging | Every API request is in the action log, marked with the token's name |

## Review and publishing pipeline

1. **Submit:** the developer runs `assistant-dev publish`. The package is signed with their developer key.
2. **Automated checks (minutes):** format and manifest valid; capabilities as narrow as possible; code and dependency scan; a sandbox run with fake accounts that records every host call.
3. **Human review** (for Verified, and for anything that sends or reads widely): a reviewer checks behavior against the description and capabilities. Target: a few business days.
4. **Sign:** approved items are signed by us.
5. **Staged release:** 5% of users first, then everyone if failure and report rates stay normal.
6. **Monitor:** failure rates, crash reports (opt-in) and user reports per item.
7. **Act fast if needed:** pull a version, roll back, or disable it everywhere with the kill switch.

Community items skip human review but still pass automated checks, and show a clear warning to users.

## Versions and compatibility

| Topic | Rule |
|---|---|
| Item versions | Semantic versions (major.minor.patch); a major version means breaking changes |
| Host interface versions | The WIT packages and the skill format each have their own version, like `assistant:plugin@1.0.0` and `skill/1` |
| Old versions keep working | The app supports at least the current and previous major versions of each interface |
| Deprecation | At least 12 months' notice before an interface version is removed, with a migration guide |
| Minimum app version | Each item states the oldest app version it works with; older apps don't offer it |
| Updates | Minor and patch updates install automatically; major updates that ask for new capabilities need the user's approval |

## Developer terms and community

### Developer agreement, in short

- Use user data only to do the task the user asked for.
- Never copy, store elsewhere, sell or use user data for training or ads.
- Declare every network destination; send nothing anywhere else.
- Follow each app's own terms when building connectors.
- Respond to security reports and fix serious problems quickly.
- Breaking these terms means removal, and loss of marketplace income.

2. Plugin host and host bindings; Rust plugins first.

4. Developer tool, test harness and docs; then other languages.
5. Marketplace, review pipeline and payments.
6. Connector toolkit, then MCP server mode.

## How we test it

| Test | What it checks |
|---|---|
| Host interface tests | Every host function behaves as specified, for each supported language |
| Sandbox escape tests | Plugins trying to reach files, network or memory outside their limits are blocked |
| Capability tests | Undeclared calls are blocked and logged |
| Resource limits | Endless loops, huge memory use and slow calls are stopped by fuel, memory and time limits |
| Token safety | No plugin can read a sign-in token in any way |
| Compatibility | Plugins built for the previous interface version still work |
| Malicious plugin red team | Security testers write harmful plugins and try to get them published |
| MCP safety | Hostile MCP servers try to hijack the planner or trigger sends |
| Marketplace flows | Buying, refunds, payouts, takedowns and the kill switch |
| Routing clashes | New skills don't steal requests from existing ones |
