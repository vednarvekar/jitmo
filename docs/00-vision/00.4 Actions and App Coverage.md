# Local Assistant Engine — 00.4 Actions and App Coverage

6 Nov 2026 · @Ved Narvekar

## Summary

This is the part that actually does things: sends the WhatsApp message, plays the song, moves the file. It is plain code, not AI. Each app gets a **connector**, which knows how to control that app.

Connectors use six control methods, always trying the most reliable one first: official APIs, Windows system APIs, deep links, the browser extension, the accessibility tree, and screen reading as a last resort.

This doc covers how each method works, how connectors are built, every v1 app in detail, sign-in, Undo, keeping connectors working when apps update, testing, legal rules, and the apps planned for later.

## Control methods

**Connectors try the most reliable method first**

| Rung | Method | Examples | |
|---|---|---|---|
| 1 | Official APIs | Gmail, Calendar, Graph | Most reliable, lightest |
| 2 | Windows system APIs | volume, files, Bluetooth | ↓ Use the next rung only if needed |
| 3 | Deep links | `spotify:`, `ms-settings:` | ↓ |
| 4 | Browser extension (v2) | web apps in Chrome | ↓ |
| 5 | Accessibility tree | WhatsApp, Spotify Play | ↓ |
| 6 | Screen reading (later) | any app, last resort | Least reliable, heaviest |

A connector can mix rungs in one task. WhatsApp, for example, opens the chat with a deep link, then sends through the accessibility tree.

**MCP tool servers (v2) are a seventh connector type, outside this ladder.** The core engine acts as an MCP client, and each MCP tool becomes a skill. They are treated as untrusted and run under the same capability limits and confirms. Details: [00.11, MCP](00.11%20Developer%20Platform.md).

## How each control method works

### 1. Official APIs

The app's company offers a web interface for programs, like the Gmail API or Microsoft Graph. The connector sends a request ("send this email") over HTTPS with the user's sign-in token, and gets a clear answer back.

- **Pros:** most reliable; doesn't break when the app's screen changes; easy to check results.
- **Cons:** needs sign-in; usage limits; some need app verification by the company.

### 2. Windows system APIs

Built-in Windows functions for things like volume, Bluetooth, files and notifications. Called directly from Rust through the `windows` crate.

- **Pros:** fast, offline, no sign-in.
- **Cons:** only for Windows features, not other apps.

### 3. Deep links

Special links that open an app at a specific place. Examples: `spotify:search:lofi` opens Spotify search; `ms-settings:bluetooth` opens Bluetooth settings; `mailto:` opens a new email.

- **Pros:** very simple; official; rarely break.
- **Cons:** usually only *open* something. Finishing the task, like pressing Play, may need another method.

### 4. Browser extension (v2)

For apps used in the browser. The extension reads the web page's structure (the DOM) and clicks or types on elements by their labels.

- **Pros:** much more reliable than reading web apps from outside.
- **Cons:** web pages change often; needs the extension installed.

### 5. Accessibility tree

Windows apps describe their screens to screen readers through UI Automation: a tree of elements like "button named Send" or "text box named Type a message." The connector finds an element by its name and type, then presses it or types into it.

- **Pros:** works for apps with no API, like WhatsApp desktop.
- **Cons:** breaks when the app changes its screen; some apps describe their screens poorly; slower than APIs.

### 6. Screen reading (later)

Take a screenshot, then use a small vision model or text recognition (OCR) to find the right button on screen and click its position.

- **Pros:** works on almost any app.
- **Cons:** heaviest on memory and slowest; least reliable; reads the screen, so it needs extra privacy care. Last resort only.

## Connector design

Every connector follows the Rust `Connector` interface from doc 07: `actions`, `health`, `execute`, `check` and `undo`. Three extra pieces make connectors easy to maintain.

In v1 our own connectors are native Rust code. Third-party connectors and plugins arrive in v2 through the sandboxed plugin host with typed (WIT) interfaces, so the interfaces are designed that way from the start (see [6.1 Tech Stack, plugin sandbox](../02-design/6.1%20-%20Tech%20Stack.md) and [00.11](00.11%20Developer%20Platform.md)). Every connector, ours included, declares its capabilities (see [07 LLD, Capabilities](../02-design/7%20-%20Low-Level%20Design.md)). At scale, routing and trust for thousands of skills are covered in [00.3, Routing at scale](00.3%20Understanding%20Engine.md).

### 1. Manifest

Each connector ships with a small manifest that describes it:

```yaml
id: whatsapp_desktop
version: 3
methods: [deep_link, accessibility]
sign_in: none            # none | oauth_google | oauth_microsoft
app_versions: ">=2.2400" # app versions this connector is tested with
actions: [open_chat, send_text, attach_and_send, read_unread]
```

### 2. Selector packs

For accessibility-tree connectors, the "where to click" details live in data files, not in code:

```yaml
send_button:
  control_type: Button
  name_any: ["Send", "Send message"]
message_box:
  control_type: Edit
  name_contains: "Type a message"
```

When an app update moves a button, we ship a new selector pack in a few KB, through the normal signed update. No app reinstall needed.

### 3. Health check

Before a task runs, the connector checks: is the app installed, running, signed in, and on a tested version? If not, the user gets a clear message before anything starts, as in doc 07's error table.

## v1 apps, one by one

### Google: Gmail, Calendar, Drive

| App | Method | Main calls | How the result is checked |
|---|---|---|---|
| Gmail | Gmail API | Search and read messages, create drafts, send, change labels | Sent message appears in Sent; labels read back |
| Google Calendar | Calendar API | List, add, change and delete events; free/busy lookup for shared free time (C2) | Event read back after saving |
| Google Drive | Drive API | Search files, read file details, create sharing permissions | Permission read back |

### Microsoft: Outlook, Calendar, OneDrive, Teams

All through Microsoft Graph, one API for all Microsoft 365 apps.

| App | Main calls | Note |
|---|---|---|
| Outlook mail | List and search messages, send mail, drafts, move to folders | Works for personal and work accounts |
| Outlook Calendar | Events; find meeting times for C2 | Meeting-time search needs a work or school account |
| OneDrive | Search, file details, create sharing links | |
| Teams | Send messages to chats and channels | Graph supports work and school Teams only, not free personal Teams |

### WhatsApp desktop

No official API for personal accounts, so this is the hardest connector.

1. **Open the chat:** a WhatsApp deep link with the contact's phone number opens their chat (to verify on the current app version).
2. **Type and send:** the accessibility tree finds the message box and Send button.
3. **Files:** the attach button, then the file picker, through the accessibility tree.
4. **Check:** read the last message in the chat and confirm it matches.
5. **Fallback:** if any step fails, open the chat with the text filled in and let the user press Send.

WhatsApp's Windows app has changed its technology more than once. Accessibility support must be re-tested with every WhatsApp update.

### Spotify

| Action | Method |
|---|---|
| Play, pause, skip, volume | Windows media controls, which work with any music app |
| Play a specific song or artist | Deep link to Spotify search, then the accessibility tree presses Play on the top result |
| Alternative | Spotify Web API; playback control there may require Premium, and Spotify limits new developer apps (to verify) |

### YouTube and websites

| Action | Method |
|---|---|
| Search YouTube or the web | Open a search URL in the default browser |
| Latest video from a creator | Find the channel once (YouTube Data API or a web lookup), cache it, then read the channel's public video feed for the newest upload |
| Open a website | Open the URL in the default browser |

### Files

| Action | Method |
|---|---|
| Find files | Windows Search index; recent files from the Windows recent list; the Downloads folder |
| Open | Open with the default app, through the Windows shell |
| Move, rename, copy | Rust file functions, with the old location saved for Undo |

### Reminders and timers

The engine's own scheduler, stored in the local database, shows Windows notifications. Windows notifications need the app to have a registered app ID, set up by the installer.

### Windows system controls

| Control | Windows feature used | Notes |
|---|---|---|
| Volume | Core Audio API | Up, down, mute, set a level |
| Brightness | WMI monitor brightness methods | Works on built-in laptop screens; most external monitors don't support it |
| Wi-Fi and Bluetooth on or off | Windows Radios API | May need the user to allow radio control once |
| Do Not Disturb | No official public API found yet (to verify) | Fallback: the accessibility tree on Quick Settings, or mute app notifications one by one |
| Lock screen | `LockWorkStation` | Instant |
| Screenshot | Windows screen capture API | Saved to Pictures\Screenshots; location shown in the result line |
| Open a settings page | `ms-settings:` deep links | For "open Bluetooth settings" style requests |
| Open or close apps | Windows shell to open; a polite close message to quit | Never force-closes an app with unsaved work |

### Web lookups

Weather and current facts can't come from a small local model. They need a web service. This is the one place with a cost per request, so it needs care.

| Need | Options | Cost note |
|---|---|---|
| Weather | Open-Meteo (free for non-commercial use; paid plan for commercial), or another weather API | Small monthly fee at our scale |
| Quick facts | Wikipedia and Wikidata APIs | Free, with fair-use limits |
| General web search | A paid search API, like Brave Search | Charged per search; must be capped |
| Creator's channel lookup | YouTube Data API | Free daily quota; results cached |

Note: Microsoft retired its Bing Search API in 2025, so that option is gone.

**Rules to keep costs and privacy under control:**

- Cache answers on the device: weather for 30 minutes, facts for a week.
- Free plan limit: a small number of web lookups per day; Pro and Team get more.
- Privacy: only the search words are sent, never names, files or messages (PS3). Requests go through our small proxy, so the provider never sees the user's IP address or account.

## Undo per action

Every "changes data" action saves what's needed to reverse it, before it runs.

| Action | How Undo works |
|---|---|
| Move, rename or copy files | Move back, rename back, or delete the copy |
| Archive or move emails | Move back to the inbox or old folder |
| Mark as read | Mark as unread |
| Create a draft | Delete the draft |
| Add an event or focus block | Delete the event |
| Set a reminder or timer | Cancel it |
| Wi-Fi, Bluetooth, Do Not Disturb | Switch back to the previous state |
| Screenshot | Delete the file |
| Save attachments to a folder | Delete the saved copies |
| Send, share, invite, decline | Can't be undone. This is why they need a confirm first. |

Undo data is kept until the toast closes, and for older actions in the action log while the change is still reversible.

## Sign-in and tokens

### How sign-in works

Google and Microsoft apps use OAuth 2.0, the standard "Sign in with Google" flow. For desktop apps, the safe version is:

1. The app opens the official sign-in page in the user's browser.
2. The user signs in and approves the permissions.
3. The browser hands a one-time code back to the app on the user's own machine (a local loopback address).
4. The app swaps the code for tokens, using PKCE, a check that stops anyone else from stealing the code.

The user's password never touches our app.

### Token rules

- **Storage:** tokens live in Windows Credential Manager, never in plain files.
- **Refresh:** access tokens are renewed in the background. If renewal fails, the user sees "Please sign in to Gmail again."
- **Fewest permissions:** ask only for what current tasks need.
- **Ask later:** reading email is asked for at first connect. Sending is asked for only the first time the user sends.
- **Disconnect:** removes tokens from the device and revokes them with Google or Microsoft.

### Approval by Google and Microsoft

Google needs app verification (weeks; start early), and Microsoft needs app registration and, for some company accounts, IT admin approval. Scope tiers, costs, timelines and recommended minimal scopes are in [9 Legal and Platform Checks, sections 4 and 5](../04-business-legal/9%20-%20Legal%20and%20Platform%20Checks.md).

## Keeping connectors working

Apps update often, sometimes weekly. API connectors rarely break. Accessibility-tree connectors, like WhatsApp and Spotify playback, break more often. This needs an ongoing process, not a one-time build.

1. **Nightly tests** run every connector against the real apps on test laptops, with the latest app versions installed automatically.
2. **Version watch:** the health check records each app's version. A new, untested version triggers a test run the same day.
3. **Fast fixes:** most breaks are fixed with a new selector pack, shipped in hours through signed updates.
4. **Safe fallback:** while broken, the connector switches to its fallback, like "I opened the chat. Press Send to finish."
5. **Error signals:** with opt-in usage stats, the team sees a spike in failures for one connector, with no message content.
6. **Owner per connector:** one engineer is responsible for each fragile connector.

## Limits, errors and offline behavior

| Situation | Behavior |
|---|---|
| API usage limit reached | Wait and retry with growing delays (backoff), up to a few seconds; then explain |
| Slow API response | Show "Working on it…" after 1 second; give up after 15 seconds with a clear message |
| Repeated reads | Cache recent lists, like contacts and recent emails, for a few minutes |
| No internet, offline task | Runs normally |
| No internet, online task | v1: explain and offer Retry. v2: offer to send it later, with a confirm when it actually goes |
| App closed (WhatsApp, Spotify) | Open it first, wait until ready, then continue |
| App asks for sign-in | Stop and tell the user; never type passwords |
| Unexpected popup in the app | Stop, don't click anything unknown, and use the fallback |

## How we build it

### Shared pieces first

1. The `Connector` interface, manifest format and health checks.
2. An OAuth helper used by every Google and Microsoft connector.
3. A UI Automation helper that reads selector packs, finds elements, waits for them and presses them.
4. A deep-link helper and a Windows shell helper.
5. The Undo store.

### Then connectors, in this order

Order follows the 15 alpha tasks in doc 08, easy ones first.

| Order | Connector | Rough effort (one engineer) |
|---|---|---|
| 1 | Windows system, files, browser, local math and astronomy | 2–3 weeks |
| 2 | Reminders and notifications | 1 week |
| 3 | Gmail and Google Calendar | 2–3 weeks |
| 4 | Outlook and Outlook Calendar (Graph) | 2 weeks |
| 5 | Spotify | 1–2 weeks |
| 6 | WhatsApp desktop | 3–4 weeks, plus ongoing upkeep |
| 7 | Google Drive, OneDrive, Teams | 2–3 weeks |
| 8 | YouTube and web lookups | 1–2 weeks |

Efforts are rough estimates for planning. With the two integrations engineers from doc 08, this fits within the alpha and beta phases.

## How we test connectors

| Test type | What it checks | When it runs |
|---|---|---|
| Unit tests with recorded API answers | Connector logic, without touching real accounts | Every code change |
| Live API tests | Real calls against the test Google and Microsoft accounts from doc 04 | Nightly |
| Live app tests | WhatsApp, Spotify and system controls driven on real test laptops | Nightly, and on every new app version |
| Undo tests | Every reversible action is done, then undone, and the state compared | Nightly |
| Matrix | Windows 10 and 11; light and dark mode; different screen scaling | Weekly |
| Failure tests | No internet, expired sign-in, app closed, unexpected popups | Weekly |

A connector can't ship unless all its tests pass and its fallback works.

## Legal and platform rules

Each needs a careful read of the current terms, ideally with a lawyer, before its connector ships. For WhatsApp, Spotify, YouTube, Google APIs and Microsoft Graph, the researched answers are in [9 Legal and Platform Checks](../04-business-legal/9%20-%20Legal%20and%20Platform%20Checks.md). Still open:

| App or service | Main question |
|---|---|
| Slack, Telegram, Discord (v2) | Whether personal-account automation is allowed at all |
| Weather and search APIs | Commercial-use licences and attribution rules |

The rule for every app: act only on the user's own account, only for actions the user asked for, and never in bulk.
